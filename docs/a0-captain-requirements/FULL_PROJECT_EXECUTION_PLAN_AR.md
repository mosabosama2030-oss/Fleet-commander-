## 0. طريقة قراءة الخطة وحالة الأدلة

### 0.1 تصنيف الادعاءات والقرارات

- **VERIFIED:** قرار بشري موثق أو حقيقة مثبتة مباشرة من وثيقة/مصدر/اختبار.
- **INFERRED:** استنتاج منطقي من الأدلة، وليس قرارًا معتمدًا.
- **PROPOSED:** اختيار هندسي مقترح ينتظر المراجعة والاعتماد.
- **UNKNOWN:** معلومة ناقصة أو قرار لم يُحسم.

### 0.2 حالات التنفيذ

- `FIXED_AND_TESTED`: نُفذ التغيير واجتاز الاختبارات المحددة مع دليل قابل للفحص.
- `PARTIAL`: نُفذ جزء، أو توجد أدلة غير مكتملة.
- `NOT_RUN`: لم يُنفذ أو لم يُختبر.
- `NOT_REQUIRED`: غير مطلوب ضمن النطاق المعتمد.
- `BLOCKED`: يتوقف على قرار أو مدخل أو اعتماد سابق.

لا تنتقل المهمة إلى `FIXED_AND_TESTED` بمجرد كتابة الكود أو نجاح اختبار واحد لا يغطي معيار القبول. ويجب أن يرتبط كل ادعاء إنجاز برقم commit أو تقرير اختبار أو نتيجة تشغيل قابلة للفحص.

## 1. الرؤية والهدف النهائي

### 1.1 الهدف

بناء نظام تشغيل وذكاء مساعد للكابتن الفردي يحوّل بيانات الشيفتات والرحلات والإيرادات والمصروفات والعداد والوقت والموقع — من مصادر يملك الكابتن حق استخدامها — إلى سجل موثوق، وحسابات قابلة للتدقيق، ومؤشرات أداء شخصية، وتقديرات وتوصيات تشرح أسبابها وحدود ثقتها.

يجب أن يساعد النظام الكابتن في الإجابة عن أسئلة عملية مثل:

1. ماذا حدث في الشيفت؟ وما الدخل والتكاليف والمبلغ المستحق والمدفوع وفق قواعد معتمدة؟
2. أين يضيع الوقت أو الكيلومترات غير المدفوعة؟
3. ما ساعات العمل والمناطق التي حققت أفضل أداء شخصي في بياناته؟
4. ما مدى دقة ETA المتاح، وما حدود تقديره؟
5. هل فرصة معلومة تستحق الوقت والمسافة والتكلفة الإضافية؟
6. هل الأفضل البقاء في المنطقة الحالية أم إعادة التموضع، بناء على البيانات المتاحة؟
7. ما سبب التوصية؟ وما البيانات التي اعتمدت عليها؟ وما المجهول؟

### 1.2 تعريف النجاح

يُعد المنتج ناجحًا عندما يستطيع كابتن واحد إتمام دورة تشغيل كاملة من الحساب إلى إغلاق الشيفت ومراجعة سجل صحيح محفوظ على الخادم، ثم استخدام تقارير وتحليلات موثوقة تساعده على اتخاذ القرار دون إخفاء عدم اليقين أو تجاوز صلاحياته.

### 1.3 ما لن يبنيه الإصدار الأول

- سوق يطابق الركاب والسائقين أو محرك dispatch متعدد السائقين.
- إدارة أساطيل أو شركات أو مشرفين أو حسابات لعدة كباتن تحت مدير واحد.
- تكامل غير رسمي أو scraping أو تجاوز حماية تطبيقات Uber أو DiDi أو غيرها.
- ادعاء معرفة الطلب أو الازدحام الحي من بيانات تاريخية شخصية فقط.
- قبول الرحلات أو تحريك المركبة أو إرسال رسائل أو تحويل أموال أو تعديل السجلات تلقائيًا.
- وكيل مستقل يتصرف بدل الكابتن.
- Deep Reinforcement Learning أو Transformer أو GNN في MVP لمجرد أن شركات كبيرة تستخدمها.
- Offline mode أو مزامنة عمليات مؤجلة في النطاق الحالي.

## 3. المنهج التنفيذي العام

**PROPOSED — المسار المعتمد لهذه الخطة:** مراحل متتابعة، ولكل مرحلة مخرجات وبوابة قبول مستقلة.

1. **A0 — إغلاق المتطلبات والقرارات.** لا كود منتج قبل هذه البوابة.
2. **A1 — التصميم التفصيلي للمجال والحسابات والعقود.** تثبيت قواعد البيانات والواجهات وسيناريوهات القبول.
3. **A2 — الأساس التقني والأمن والتشغيل.** مشروع قابل للبناء والاختبار مع المصادقة والبيانات والترحيلات.
4. **D1 — التشغيل الأساسي.** ملف الكابتن والمركبات والشيفتات والرحلات/الإيرادات والمصروفات والحسابات والسجل.
5. **D2 — التقارير والتحليلات الشخصية.** مؤشرات فعلية وجودة البيانات وETA/التوقعات الأساسية عند توفر البيانات.
6. **D3 — دعم القرار.** تقييم الفرص وإعادة التموضع وتخطيط الشيفت والمساعد التفسيري.
7. **D4 — التحقق والتشغيل التدريجي.** Replay وShadow mode وتجربة محدودة ومراقبة وخطة رجوع.
8. **التوسع اللاحق.** ميزات اختيارية مشروطة ببيانات ومصادر وقرار جديد.

لا يتم تجاوز بوابة مرحلة لمجرد أن الواجهة تبدو جاهزة. يجب أن تجتاز الوظيفة عقودها واختباراتها، وأن تكون حالات الفشل واضحة، وأن توجد أدلة قبول.

## 4. المعمارية المستهدفة

### 4.1 النمط المعماري

**PROPOSED:** Modular Monolith في البداية، مع واجهة API واحدة مشتركة بين Web وAndroid، وحدود داخلية واضحة بين المجال والتطبيق والتخزين والتكاملات والتحليلات.

السبب: مستخدم الإصدار الأول فردي، ولا توجد حتى الآن أحجام حمل أو احتياجات تشغيل تبرر Microservices أو Kafka أو Flink أو Spark أو بنية متعددة الخدمات. يمكن فصل خدمة لاحقًا عندما يثبت القياس وجود حاجة فعلية.

### 4.2 الطبقات

1. **Presentation:** واجهة عربية RTL متجاوبة، مع تجربة Mobile-first، وتطبيق Android يعرض الوظائف الأساسية نفسها.
2. **API / Application:** المصادقة، التفويض، التحقق، تنسيق حالات الاستخدام، حدود المعدل، idempotency، ومعالجة الأخطاء.
3. **Domain:** قواعد الكابتن والمركبة والشيفت والرحلة والإيراد والمصروف والتسوية وقواعد الحساب المعتمدة.
4. **Persistence:** قاعدة بيانات خادمية وترحيلات Schema ومستودعات وصول، مع قيود ملكية وعلاقات وفهارس.
5. **Integrations:** مزود الخرائط، رفع الملفات، التصدير، الإشعارات وأي مصادر رسمية معتمدة؛ كل تكامل خلف Adapter محدد.
6. **Analytics:** الاستعلامات والتجميعات والخطوط الأساسية وحساب المؤشرات، منفصلة عن واجهة العرض.
7. **Decision Intelligence:** ETA والتوقعات وتقييم الفرص وإعادة التموضع، لا تملك صلاحية كتابة السجلات التشغيلية.
8. **LLM Assistant:** فهم السؤال واختيار أداة تحليل مسموح بها وشرح النتائج؛ لا ينفذ SQL حرًا ولا يحسب المال ولا يقرر بدل الكابتن.
9. **Observability:** سجلات منظمة ومقاييس وتتبع أخطاء وتنبيهات مع حجب الأسرار والبيانات الشخصية.

### 4.3 حدود الوحدات المقترحة

أسماء المجلدات التالية **مقترحة وليست وصفًا لملفات موجودة**. يتم تثبيتها بعد اعتماد اللغة والإطار:

- `domain/`: نماذج المجال وقواعده.
- `application/`: حالات الاستخدام والخدمات المنسقة.
- `api/`: المسارات ومخططات الطلب/الاستجابة والتحقق.
- `infrastructure/persistence/`: قاعدة البيانات والترحيلات والمستودعات.
- `integrations/maps/`, `integrations/files/`, `integrations/exports/`: موصلات خارجية محدودة.
- `analytics/`: KPIs وData Quality وBaselines.
- `intelligence/eta/`, `intelligence/forecasting/`, `intelligence/opportunity/`, `intelligence/repositioning/`: وحدات القرار.
- `assistant/`: طبقة المحادثة وتوجيه الأدوات والتفسير.
- `tests/unit/`, `tests/integration/`, `tests/contracts/`, `tests/security/`, `tests/replay/`: طبقات الاختبار.

يُمنع نقل منطق الحساب إلى مكونات الواجهة أو إلى Prompt النموذج اللغوي.

### 5.2 قواعد البيانات وسلامتها

- كل سجل مملوك للكابتن يحمل مرجع مالك يُشتق من الجلسة المصادق عليها على الخادم، لا من قيمة موثوقة يرسلها المتصفح.
- **لا نفترض نظام شركات أو `tenant_id` في الإصدار الأول.** عزل حسابات الكباتن يطبق عبر `owner_user_id`/ملكية المورد على كل قراءة وكتابة وتصدير. إعادة تصميم multi-tenant تتطلب قرار نطاق لاحق.
- استخدام مفاتيح خارجية وقيود فريدة وفهارس مرتبطة بالمالك عند الحاجة.
- حفظ الوقت داخليًا بصيغة موحدة (UTC) وتسجيل/عرض المنطقة الزمنية المعتمدة بوضوح؛ لا تخلط وقت الجهاز مع وقت الخادم بلا سياسة.
- حفظ النقود بدقة عشرية أو بوحدات العملة الصغرى المعتمدة؛ **يمنع استخدام floating-point للحساب المالي**.
- أي تصحيح مالي يجب أن يترك أثر تدقيق. اعتماد append-only/correction entries أو آلية تعديل مضبوطة قرار يُحسم في A0/A1.
- عمليات الإنشاء التي يمكن أن تتكرر بسبب timeout تدعم `Idempotency-Key` أو كشف تكرار موثق.
- الترحيلات قابلة للتراجع أو لها خطة إصلاح/استعادة موثقة؛ لا تعديل Schema يدوي غير مسجل في الإنتاج.

### 5.3 قاموس الحقول

قبل بناء أي نموذج يجب تحديد لكل حقل: `field_id`، المعنى، النوع، الوحدة، العملة إن وجدت، المصدر، المالك، الإلزامية، قواعد التحقق، سياسة الخصوصية، مدة الاحتفاظ، وقاعدة التعديل/الحذف.

## 6. عقد API وسلوك التطبيقات

**PROPOSED:** API موحدة ذات إصدار واضح، بواجهات JSON ذات مخططات ثابتة. التقنية النهائية والمصادقة تُحسم في A0.

### 6.1 مجموعات العقود

- Auth: إنشاء/إنهاء جلسة، استعادة الحساب، عرض المستخدم الحالي.
- Profile & Vehicles: الملف والمركبات المملوكة.
- Shifts: إنشاء الشيفت، عرضه، إنهاؤه، وتصحيحاته المسموحة.
- Trips & Revenue: الإدخال والاستيراد المصرح به والتحقق ومنع التكرار.
- Expenses & Settlements: المصروفات والتسويات والإثباتات.
- Reports: ملخصات الفترات والتفاصيل والتصدير.
- Analytics: مؤشرات فعلية وبيانات الجودة والخطوط الأساسية.
- Intelligence: ETA والتوقعات وتقييم الفرص والتوصيات.
- Assistant: سؤال مسموح، استدعاء أداة محددة، وإجابة مرتبطة بالأدلة.

### 6.2 عقد الخطأ الموحد

كل استجابة خطأ يجب أن تحمل رمزًا ثابتًا قابلًا للمعالجة، ورسالة عربية آمنة، ومعرف تتبع، وما إذا كان التكرار الآمن مسموحًا. تشمل الحالات: `400` مدخل غير صالح، `401` غير مصادق، `403` غير مصرح، `404` غير موجود/غير مملوك، `409` تعارض حالة/تكرار، `413` حجم ملف مرفوض، `422` قاعدة مجال مرفوضة، `429` حد معدل، `5xx` خطأ خادمي.

لا تعرض الواجهة نجاح الحفظ قبل تأكيد الخادم. بعد timeout لا تعيد إنشاء سجل مالي عشوائيًا؛ تستعلم عن نتيجة العملية أو تعيد الطلب بمفتاح idempotency ثابت.

### 6.3 التكافؤ بين Web وAndroid

تعتمد الواجهتان نفس API وقواعد المجال، مع اختبارات Contract مشتركة. لا يُسمح بأن تنفذ كل واجهة حسابًا ماليًا مختلفًا أو تخزن السجل التشغيلي في مخزن محلي مستقل.

## 9. منهجية البيانات والذكاء الاصطناعي

### 9.1 هرم الثقة في البيانات

1. سجل تشغيلي أكده الكابتن أو مصدر رسمي مصرح به.
2. قيمة محسوبة deterministic من حقول موثوقة وقواعد معتمدة.
3. قيمة مقدرة من مزود أو نموذج مع اسم المصدر والوقت.
4. استنتاج مشتق مع توضيح السبب والحدود.
5. قيمة مجهولة `UNKNOWN` إذا لم تتوفر أدلة كافية.

لا يجوز ترقية inference إلى actual، أو عرض estimated على أنه قيمة مؤكدة.

### 9.2 البيانات والخصوصية

- جمع أقل قدر لازم من البيانات لكل غرض.
- GPS أو بيانات الموقع لا تجمع إلا بموافقة صريحة وغرض معلوم ومدة احتفاظ محددة.
- فصل بيانات المصدر الخارجي عن سجل الكابتن؛ لا تُدمج بيانات السوق في السجل المالي كحقيقة.
- دعم سحب الموافقة وإيقاف المعالجة المستقبلية وفق السياسة المعتمدة.
- تحديد سياسة حذف/تصدير ومدة الاحتفاظ قبل الإطلاق.
- عدم تخزين Tokens أو كلمات مرور أو مفاتيح API في العميل أو logs.

### 9.3 بناء نموذج أولي وتدريبه

1. إنشاء Baseline بسيط قبل أي ML.
2. تقسيم البيانات زمنيًا: train ثم validation ثم test أحدث زمنيًا؛ لا تقسيم عشوائي فقط.
3. منع Data Leakage: الميزات لا تستخدم معلومات لم تكن متاحة لحظة التوصية، ولا تستخدم نتيجة الرحلة ضمن ميزات التنبؤ بها.
4. قياس الأداء الإجمالي وحسب الساعة والمنطقة ونوع الرحلة وحجم العينة.
5. حفظ نسخة البيانات والميزات ومعلمات النموذج ووقت التدريب وكود الإصدار.
6. قياس calibration ونطاقات التنبؤ؛ لا تعرض نسبة ثقة إلا إذا عُرفت طريقة معايرتها.
7. مراقبة drift وخطأ التنبؤ وحداثة البيانات.
8. إيقاف النموذج أو الرجوع للBaseline عند تدهور مقاييس متفق عليها.

### 9.4 المقاييس المقترحة

- ETA: MAE، Median Absolute Error، P90 error، والانحياز حسب الشريحة.
- توقع الأداء الشخصي: MAE/Pinball Loss للنطاقات، مع مقارنة Seasonal Naive/Median baseline.
- ترتيب الفرص: Precision@K/NDCG@K فقط إذا توفرت labels صالحة لنتائج الفرص؛ وإلا يعلن التقييم محدودًا.
- جودة البيانات: precision/recall على حالات مراجعة بشرية، ومعدل الإنذارات الكاذبة.
- التوصيات: معدل عرض التوصية، القبول الاختياري، النتيجة الفعلية، والتأثير على الوقت/التكلفة؛ لا ادعاء السببية من replay وحده.

لا تُخترع حدود دنيا عامة لحجم العينة. تُحدد بعد تحليل البيانات والتباين ومقاييس الثقة؛ وعند عدم الكفاية يرجع النظام إلى UNKNOWN أو baseline.

### 9.5 سجل التوصية الإلزامي

كل توصية يجب أن تتضمن:

- `recommendation_id` ووقت الإنشاء ومدة الصلاحية.
- السؤال/الهدف الذي تحاول الإجابة عنه.
- سجل المصدر أو مصدر البيانات وتاريخ رصده وحداثته.
- الفترة وحجم العينة.
- القيم الفعلية والمقدرة والمستنتجة والمجهولة كلٌّ على حدة.
- العوامل الأساسية وطريقة الحساب/إصدار النموذج.
- الثقة أو نطاق عدم اليقين ومعنى هذا المقياس.
- القيود والتحذيرات وسبب عدم التوصية عند وجوده.
- اختيار الكابتن والنتيجة الفعلية عند توافرها.

## 10. دور LLM وحدوده

### 10.1 مسموح

- تفسير سؤال المستخدم وتحديد النية والفترة والكيان.
- طلب توضيح واحد عند غموض يمنع تنفيذ استعلام آمن.
- اختيار أدوات قراءة وتحليل مسموح بها من قائمة محددة.
- شرح نتائج الحساب والتحليل وربط كل claim بدليل أو calculation ID.
- تلخيص أسباب التوصية وبيان البيانات الناقصة.

### 10.2 غير مسموح

- احتساب الأجرة أو المصروف أو الصافي أو العمولة داخل النموذج اللغوي.
- إنشاء SQL حر أو تنفيذ أوامر قاعدة بيانات مباشرة.
- قراءة حساب آخر أو تخطي authorization.
- اختلاق مصدر أو ETA أو حافز أو طلب حي.
- إنشاء أو تعديل أو حذف سجل مالي دون مسار معتمد وتأكيد بشري.
- قبول رحلة أو إرسال رسالة أو تحريك المركبة أو تنفيذ تحويل أو إجراء خارجي.

### 10.3 بنية الإجابة

يجب أن يستطيع النظام إرجاع نتيجة منظمة، مثل: `answer_claims[]`، `evidence_refs[]`، `calculations[]`، `period`، `freshness`، `sample_size`، `confidence`، `limitations`، `unknowns[]`. النص الطبيعي يشرح هذه البيانات ولا يستبدلها.

يُختبر الربط على مستوى كل ادعاء، لا بمجرد إضافة قائمة مصادر في نهاية الإجابة. أي ادعاء رقمي بلا دليل/حساب واضح يُحذف أو يتحول إلى UNKNOWN.

## 11. استراتيجية الاختبار والتحقق

### 11.1 طبقات الاختبار

| النوع | الغرض | أمثلة حاسمة |
|---|---|---|
| Unit | اختبار قواعد صغيرة | حساب المال، تقريب العملة، حدود الوقت، انتقالات الشيفت |
| Property-based | حالات كثيرة وخصائص عامة | لا دخل سالب غير مسموح، الجمع متسق، idempotency لا يضاعف |
| Integration | مكونات حقيقية معًا | API + DB + auth + file storage + transactions |
| Contract | توافق Web/Android مع API | schema/errors/versioning/parity |
| End-to-End | رحلة كابتن كاملة | دخول → شيفت → رحلة → مصروف → إغلاق → تقرير |
| Security | ملكية وصلاحيات ومدخلات | A/B isolation، IDOR، XSS، CSRF حسب التقنية، uploads، SSRF عند وجود جلب URL |
| Replay/ML | تقييم تنبؤ/توصية | time split، leakage، baseline، calibration، drift |
| Load/Resilience | تحمل الأعطال والضغط | rate limit، timeout، DB restart، retries، backup restore |
| Manual UX | اختبار الاستخدام الحقيقي | RTL، قراءة الأرقام، حالات empty/loading/error، شاشات Android مختلفة |

### 11.2 الحالات الحرجة الإلزامية

1. حسابان منفصلان يحاول كل منهما قراءة/تعديل/تصدير بيانات الآخر: يجب الرفض على الخادم.
2. طلب إنشاء متكرر بعد timeout: لا ينشئ سجلًا ماليًا مضاعفًا.
3. شيفت يعبر منتصف الليل أو يتداخل أو يغلق مرتين: النتيجة تتبع قواعد A0 فقط.
4. اختلاف قيمة أو وحدة أو عملة أو قراءة عداد: يُظهر تعارضًا ولا يصحح تلقائيًا.
5. خريطة أو إشارة سوق قديمة أو غير متاحة: لا يعرضها النظام كبيانات حية.
6. سجل قصير أو مستخدم جديد: لا يختلق baseline أو توصية؛ يعلن insufficient data.
7. سؤال ملتبس أو فترة زمنية غير محددة: لا يخترع الفترة أو الكيان.
8. prompt injection داخل نص رحلة أو ملف: يعامل كبيانات غير موثوقة، لا كتعليمات.
9. فشل قاعدة البيانات أو رفع الملف: لا يعلن نجاحًا ولا يفقد أثر المحاولة.
10. تصدير تقرير: يضم بيانات الحساب نفسه فقط ويُسجل في AuditEvent.

### 11.3 أوامر التشغيل

أوامر الاختبار النهائية لا تثبت في هذه الخطة لأن لغة البرمجة وأداة البناء لم تُحسما بعد. بعد A0-16 يجب تحديد أوامر ثابتة في `CONTRIBUTING` أو CI لكل من:

- تثبيت الاعتماديات بإصدارات مقفلة.
- Format/Lint/Type-check.
- Unit/Property tests.
- Integration/Contract tests.
- Security/dependency scan.
- Build Web وBuild Android.
- E2E/Smoke لكل بيئة.

لا يكتب في تقرير الإنجاز أن اختبارًا نجح إلا مع اسم الأمر والبيئة وcommit SHA ومخرجاته الفعلية.

## 12. الأمن والخصوصية والاستجابة للحوادث

### 12.1 ضوابط أمنية

- Authorization في كل endpoint وعلى مستوى كل مورد، وليس في إخفاء زر الواجهة.
- جلسات آمنة ومدة صلاحية وإبطال وتدوير أسرار ومقاومة تخمين الدخول.
- Rate limiting وقيود حجم الطلبات والمرفقات.
- حماية XSS وCSRF وفق نمط المصادقة، وCORS بقائمة origins محددة، وSecurity headers.
- SSRF defense إذا استُقبلت روابط أو استُخدم جلب خارجي: رفض localhost/private/link-local/metadata IPs والتحقق من redirect/DNS وفق التصميم.
- التحقق من MIME الفعلي والامتداد والحجم وفحص الملفات عند توفر آلية مناسبة.
- سجلات لا تحتوي كلمات مرور أو tokens أو بيانات مالية حساسة غير لازمة.
- مراجعة اعتماديات وثغرات وSBOM إن دعمت بيئة البناء.
- فصل الأسرار بين dev/staging/prod؛ لا مشاركة سر الإنتاج مع الاختبارات.

### 12.2 الخصوصية

يجب اعتماد Privacy/Data Retention Matrix توضح البيانات، الغرض، الحساسية، مكان التخزين، من يقرأها، مدة الاحتفاظ، التصدير، الحذف، وسحب الموافقة. لا يبدأ التتبع المكاني المستمر افتراضيًا.

### 12.3 الحوادث

تعريف مسار للإبلاغ عن تسريب أو وصول غير مصرح به: تعطيل السر/الجلسة، تحديد النطاق، حفظ الأدلة، إيقاف الوظيفة المتأثرة، إخطار صاحب القرار، استعادة آمنة، ثم تقرير سبب جذري وإجراءات منع تكرار. تفاصيل الالتزامات التنظيمية تحتاج مراجعة قانونية محلية قبل الإنتاج.

## 13. البيئات والنشر والتشغيل

### 13.1 البيئات

- `dev`: تطوير ببيانات اصطناعية أو منقحة؛ لا أسرار إنتاج.
- `test/CI`: اختبارات معزولة وقابلة للتكرار.
- `staging`: نسخة قريبة من الإنتاج مع بيانات اختبار غير حقيقية.
- `production`: بيانات الكابتن الحقيقية، وصلاحيات وأسرار ومراقبة ونسخ احتياطي مشددة.

### 13.2 بوابة النشر

1. فحص تغييرات PR ومراجعة الكود.
2. نجاح lint/type/unit/integration/contract/security checks.
3. ترحيل قاعدة البيانات في staging وتجربة العودة/الإصلاح.
4. Smoke test للمصادقة والشيفت والتسجيل والتقارير والتصدير.
5. تأكيد backup حديث وقابل للاستعادة.
6. موافقة بشرية على نشر الإنتاج.
7. مراقبة بعد النشر ومقارنة الأخطاء والمؤشرات مع baseline.
8. تشغيل rollback أو kill switch عند تجاوز حدود الفشل.

### 13.3 مؤشرات التشغيل

- API availability/error rate/latency p50-p95-p99.
- DB connection/latency/error/backup status.
- auth failures/rate-limit/security events.
- upload/export failures.
- data freshness and missingness.
- prediction MAE/bias/calibration/drift عند تشغيل ML.
- assistant tool errors وunsupported/unknown answer rate.

تحدد SLO thresholds بعد اختيار الاستضافة وتقدير الاستخدام. لا تُسجل قيم رقمية افتراضية على أنها التزام معتمد.
