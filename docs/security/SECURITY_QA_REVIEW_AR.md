## 1. الملخص التنفيذي

**النتيجة:** توجد نواة مجال واختبارات برمجية وواجهة عرض، لكن `main` لا يقدم بعد منظومة هوية وجلسات إنتاجية، ولا تخزينًا دائمًا أو مرفقات أو GPS أو تصديرًا أو سجل تدقيق دائمًا. لذلك لا ينبغي تفسير وجود اختبارات نطاق أو مسودة تصميم أمني على أنه إثبات جاهزية أمنية أو إغلاق A0.

أعلى فجوات الإطلاق:
1. **P0 — المصادقة والتفويض الإنتاجيان غير موجودين في main.** نواة FleetService تستقبل `ownerUserId` من مستدعيها؛ لا توجد طبقة حسابات/جلسات/هوية موثقة مدمجة في main. PR #41 المفتوح Draft يقدم رمز Bearer ثابتًا مشتركًا ومالكًا واحدًا مضبوطًا بالخادم لأغراض التطوير فقط، ويصرح بأنه ليس مصادقة إنتاجية.
2. **P0 — لا يوجد عزل متعدد الحسابات قابل للاعتماد عبر حد HTTP/قاعدة بيانات.** اختبارات النواة تثبت أن بعض عمليات المجال تقيد السجلات بالمالك الذي يمرر إليها، لكنها لا تثبت أن هذا المعرّف مشتق من هوية مصادق عليها في كل طلب، أو أن العزل محفوظ في قاعدة بيانات دائمة.
3. **P0 — لا توجد قاعدة بيانات دائمة أو تشغيل/استعادة مثبتة.** التخزين الحالي في الذاكرة؛ ضياع البيانات عند إعادة التشغيل متوقع، ونسخ Backup/Restore الفعلي غير مثبت.
4. **P1 — GPS والمرفقات والتصدير والاحتفاظ والحذف غير منفذة.** توجد متطلبات/تصاميم مقترحة على فرع غير مدمج فقط؛ لا توجد أدلة تشغيلية تثبت الموافقة أو الإيقاف أو الملكية أو سياسات الاحتفاظ.
5. **P1 — سجل التدقيق محدود بالذاكرة والنطاق الحالي.** وجود AuditEvent في النواة لا يثبت سجلًا دائمًا محميًا أو تدقيقًا لمحاولات الدخول والتصدير وتغيير كلمة المرور.
6. **P1 — تنقيح البيانات قبل LLM ليس ضمان خصوصية كافيًا وحده.** الـGateway مغلق افتراضيًا وميزانيته صفر (ضابط إيجابي)، لكن التنقيح قائم على أنماط ولا يكتشف الأسماء/العناوين النصية الحرة، ولا يغني عن تقليل البيانات والتحكم الصارم في الغرض والموافقة.

لا أوصي بإعلان G0/G1 أو إطلاق إنتاجي بناءً على هذه الأدلة وحدها. يجب أن تبقى القرارات البشرية المفتوحة ونتائج NOT_RUN ظاهرة.

## 3. النتائج حسب الأولوية

### P0 — مانع قبل أي استخدام إنتاجي

#### SEC-001 — لا توجد مصادقة/جلسات إنتاجية في main

- **الدليل:** لا توجد في شجرة main التي فُحصت وحدات تسجيل حساب أو تحقق بريد/كلمة مرور أو جلسة/رمز مستخدم أو استعادة حساب. `FleetService` يأخذ `ownerUserId` كوسيط من المستدعي؛ النواة لا تتحقق من هوية الشخص الذي استدعاه.
- **التصنيف:** VERIFIED — غياب هذه الطبقة عن الملفات/الشجرة المفحوصة في main. UNKNOWN — ما إذا كانت هناك بيئة خارج المستودع غير موثقة.
- **الأثر:** إذا تم كشف مسارات المجال مباشرة أو ربطها بطبقة HTTP لا تتحقق من هوية موثوقة، يصبح انتحال owner أو الوصول غير المصرح به ممكنًا. لا يوجد في main خادم HTTP منشور، لذا هذه فجوة إطلاق/تصميم وليست ادعاءً بوجود endpoint عام مستغل حاليًا.
- **الاختبار المطلوب:** `T-AUTH-01`: طلب بلا بيانات اعتماد إلى كل endpoint محمي ⇒ 401؛ رمز غير صالح/منتهي/ملغى ⇒ 401؛ رمز صالح ⇒ حساب صاحبه فقط. `T-AUTH-02`: استعادة كلمة المرور برمز أحادي الاستخدام، محدود الصلاحية، لا يكشف وجود الحساب.
- **معيار الإغلاق:** هوية موثقة من جلسة/رمز مصادق عليه على الخادم؛ كلمات مرور مجزأة بخوارزمية حديثة؛ انتهاء/إبطال الجلسات؛ rate limiting؛ عدم كشف وجود الحساب؛ اختبارات HTTP integration لكل المسارات.
- **الحالة:** NOT_RUN على main.

#### SEC-002 — إثبات الملكية على مستوى المجال لا يثبت عزل الهوية على مستوى الطلب والتخزين

- **الدليل:** توجد دوال مثل `#ownedShift` و`#ownedTrip` وتصفية حسب `ownerUserId` في FleetService. توجد اختبارات ملكية في النواة. لكن هذا لا يثبت مصدر `ownerUserId` من جلسة موثقة ولا قيودًا دائمة في قاعدة البيانات. PR #41 المقترح يستخدم `FC_OWNER_ID` ثابتًا من إعداد الخادم؛ هذا وضع تطوير لكابتن واحد، وليس مصادقة متعددة الحسابات.
- **التصنيف:** VERIFIED — حدود النواة الحالية واختباراتها؛ VERIFIED — وصف PR #41 وحدوده؛ UNKNOWN — عزل persistence المستقبلي.
- **الأثر:** خطر BOLA/IDOR عند أي endpoint يسمح للعميل بتحديد المالك أو ينسى شرط الملكية في استعلام أو تصدير.
- **الاختبارات المطلوبة:** `T-ISO-01`: حساب A ينشئ موردًا؛ حساب B يحاول قراءته/تعديله/إغلاقه/إلغاءه/تصحيحه ⇒ 404 أو استجابة عدم كشف متفق عليها ولا يتغير المورد. `T-ISO-02`: اختبارات لكل قائمة وتفصيل ومرفق وتصدير، مع محاولات تغيير IDs في URL/body/query. أضف اختبارات قاعدة بيانات لحواجز المالك/tenant عند اعتماد DB.
- **معيار الإغلاق:** استخراج owner من سياق مصادقة موثوق فقط؛ تجاهل/رفض owner IDs المرسلة من العميل؛ تضمين قيد الملكية في كل استعلام؛ اختبارات سلبية على جميع العمليات والموارد، لا على shift/trip فقط.
- **الحالة:** PARTIAL للنواة؛ NOT_RUN لحد HTTP/DB الكامل.

#### SEC-003 — التخزين مؤقت ولا توجد استعادة بيانات مثبتة

- **الدليل:** FleetService يصرح أن خرائط المركبات والشيفتات والرحلات والتصحيحات وسجل التدقيق في الذاكرة. PR #41 يصرح بأن التخزين ephemeral ويضيع عند restart. PR #44 يحتوي قائمة تحقق Backup/Restore توثيقية فقط؛ لا يثبت مزودًا أو نسخة أو استعادة.
- **التصنيف:** VERIFIED — التخزين الحالي في الذاكرة؛ UNKNOWN — قاعدة البيانات ومزود النسخ وRPO/RTO.
- **الأثر:** فقد سجلات التشغيل والتصحيحات وأدلة التدقيق عند إعادة تشغيل العملية أو فقد المضيف.
- **الاختبارات المطلوبة:** `T-PERSIST-01`: اكتب سجلات ثم أعد تشغيل الخدمة وتحقق من بقائها. `T-BKP-01`: استعادة نسخة في بيئة معزولة والتحقق من counts/integrity. اختبارات migrations، التزامن، الفشل الجزئي، وidempotency عبر restart.
- **معيار الإغلاق:** DB معتمدة بقرار MOSAAB، migrations، تشفير نقل/تخزين وفق قدرات المزود، سياسة Backup موثقة، Restore ناجح فعليًا مع قياس RPO/RTO، وضوابط أقل صلاحية.
- **الحالة:** NOT_RUN؛ لا يُدعى وجود Backup/Restore فعلي.

### P1 — مرتفع

#### SEC-004 — GPS consent/withdrawal/retention غير منفذ

- **الدليل:** لا يستخدم `web/app.js` واجهة `navigator.geolocation` ولا توجد خدمة GPS في الملفات التي فُحصت. نموذج التهديد وتصميم A1 على session/05 يقترحان جمع الموقع فقط أثناء OPEN وبموافقة صريحة، وإيقافه عند الإغلاق أو سحب الموافقة، لكنهما PROPOSED/NOT RUN؛ مدة الاحتفاظ وفترة أخذ العينات والحذف ما زالت مفتوحة.
- **التصنيف:** VERIFIED — عدم وجود تكامل GPS في واجهة main المفحوصة؛ VERIFIED — حالة المستندات المقترحة؛ UNKNOWN — سياسة الاحتفاظ النهائية.
- **الأثر:** لا يوجد دليل على أن المنتج يجمع الموقع حاليًا؛ لكن إضافة GPS قبل اعتماد السياسة واختبارها قد تؤدي إلى تتبع زائد أو استمرار الجمع بعد سحب الموافقة.
- **الاختبارات المطلوبة:** `T-GPS-01`: رفض الإذن ⇒ لا جمع ولا إعادة طلب متكرر. `T-GPS-02`: موافقة فعالة + شيفت OPEN ⇒ جمع مسموح فقط وفق sampling المعتمد. `T-GPS-03`: سحب الموافقة أو إغلاق الشيفت ⇒ إيقاف فوري ورفض نقاط لاحقة على الخادم. `T-GPS-04`: رفض الإرسال خارج النطاق الزمني/حالة الشيفت؛ اختبار صلاحيات الموقع على Android وPWA foreground/background بصورة منفصلة.
- **معيار الإغلاق:** اعتماد مدة الاحتفاظ والفاصل والغرض والحذف والتصدير من MOSAAB؛ ConsentGrant مسجل ومؤرخ وقابل للسحب؛ مؤشر ظاهر؛ enforcement خادمي؛ اختبارات على حالات الإذن/الرفض/السحب/الإغلاق؛ لا ادعاء بتتبع PWA في الخلفية دون إثبات جهاز فعلي.
- **الحالة:** NOT_RUN.

#### SEC-005 — المرفقات غير موجودة، وضوابط رفع/تنزيل الملفات مقترحة فقط

- **الدليل:** لا توجد مسارات upload/download أو خدمة تخزين مرفقات في شجرة main المفحوصة. session/05 يقترح JPEG/PNG وmagic bytes وحد 5MB وتخزينًا خاصًا وروابط موقعة؛ المقترحات لم تُنفذ.
- **التصنيف:** VERIFIED — لا implementation ظاهر في main؛ PROPOSED — تفاصيل الضوابط في A1.
- **الأثر:** عند إضافة إيصالات/صور عداد دون هذه الضوابط، تظهر مخاطر ملفات خبيثة، MIME spoofing، كشف روابط عامة، تجاوز ملكية، وموارد كبيرة.
- **الاختبارات المطلوبة:** `T-ATT-01`: رفض نوع/محتوى لا يطابق allowlist، امتداد مزيف، ملف تالف، حجم زائد، واسم ملف خبيث. `T-ATT-02`: حساب آخر لا يستطيع تنزيل الملف؛ الرابط الموقع قصير العمر ومحدود المورد؛ فحص عدم التنفيذ و`nosniff`.
- **معيار الإغلاق:** قرار بشري للأنواع/الحجم/الاحتفاظ؛ فحص magic bytes؛ أسماء داخلية عشوائية؛ تخزين غير عام؛ authorization عند كل تنزيل؛ حدود الحجم ومعدل الرفع؛ اختبارات ملكية ونوع/حجم.
- **الحالة:** NOT_RUN.

#### SEC-006 — سجل التدقيق ليس سجلًا أمنيًا دائمًا ومتكاملًا

- **الدليل:** AuditEvent في FleetService يغطي أحداث نطاقية معينة ويخزنها في مصفوفة ذاكرة؛ لا يوجد دليل main على تخزين دائم أو سجل لمحاولات المصادقة الفاشلة، تغييرات الحساب، التصدير أو الوصول الإداري. تصميم A1 يقترح Structured logs وrequest_id وAuditEvent لكنّه NOT RUN.
- **التصنيف:** VERIFIED — سجل المجال مؤقت ومحدود؛ UNKNOWN — بنية logging/persistence النهائية.
- **الأثر:** صعوبة التحقيق في إساءة الاستخدام أو إثبات من قرأ/صدر/غيّر بيانات حساسة.
- **الاختبارات المطلوبة:** `T-LOG-01`: كل عملية حساسة تسجل actor/resource/action/time/result/request_id؛ لا تسجل كلمة مرور أو token أو محتوى GPS أو payload حساس؛ لا يستطيع المستخدم العادي تعديل أو حذف سجل التدقيق.
- **معيار الإغلاق:** سجل append-only دائم أو مخزن محمي مع سياسة وصول واحتفاظ؛ أحداث قراءة/تصدير/مصادقة حساسة وفق مبدأ تقليل البيانات؛ redaction مثبت باختبارات.
- **الحالة:** PARTIAL للنواة؛ NOT_RUN لسجل أمني دائم.

#### SEC-007 — التصدير والحذف وسياسة الاحتفاظ غير معرفة/منفذة

- **الدليل:** المتطلبات تتضمن التصدير، لكن لا توجد عملية تصدير أو حذف حساب مثبتة في الملفات التي فُحصت. DEC-14/الاحتفاظ تظهر UNKNOWN أو مفتوحة في مصادر A0 غير المدمجة.
- **التصنيف:** VERIFIED — غياب تنفيذ ظاهر؛ UNKNOWN — المدد والالتزامات وسياسة الحذف.
- **الأثر:** خطر تسرب بيانات عند بناء export بلا authorization، أو احتفاظ غير مبرر/حذف غير متسق بين البيانات والمرفقات والنسخ.
- **الاختبارات المطلوبة:** `T-EXP-01`: حساب A لا يصدر إلا بياناته؛ التصدير يسجل AuditEvent؛ لا توجد روابط عامة أو ملفات قابلة للتخمين. `T-RET-01`: اختبار آلي لمواعيد الاحتفاظ والحذف/الإخفاء وفق السياسة المعتمدة مع توثيق أثر النسخ الاحتياطية.
- **معيار الإغلاق:** قرار MOSAAB موثق بشأن مدد الاحتفاظ والحذف/التصدير؛ تحقق ملكية الخادم؛ سجلات تدقيق؛ اختبار ملفات التصدير وبياناتها الوصفية والروابط؛ مسار حذف متسق مع backup/legal hold إن وجد.
- **الحالة:** NOT_RUN.

#### SEC-008 — تنقيح LLM لا يغني عن تقليل البيانات وموافقة المستخدم

- **الدليل:** `SAFE_DEFAULT_CONFIG` يجعل الـGateway والأغراض معطلة والميزانية اليومية صفرًا؛ هذه حماية إيجابية. `redact.ts` ينقح البريد وبعض تسلسلات الأرقام والإحداثيات، ويذكر صراحة أن الأسماء والعناوين الحرة لا تُنقح بشكل موثوق. gateway يرسل الرسائل بعد التنقيح إلى provider إذا فُعّل config؛ لا توجد أدلة على مزود فعلي مفعّل في main.
- **التصنيف:** VERIFIED — الإعداد الافتراضي المغلق وقواعد التنقيح؛ UNKNOWN — أي تكوين نشر خارجي غير موثق.
- **الأثر:** تفعيل مزود قبل تحديد الغرض والبيانات المسموح بها قد يكشف أسماء أو عناوين أو تفاصيل تشغيلية؛ regex لا يمثل anonymization.
- **الاختبارات المطلوبة:** `T-AI-PRIV-01`: مجموعة اختبار عربية/إنجليزية تتضمن بريدًا وأرقامًا وهواتف وإحداثيات وأسماء وعناوين ونصوصًا مشوشة؛ افحص ما يصل إلى provider mock. `T-AI-PRIV-02`: deny-by-default عند غياب consent/purpose/provider allowlist أو budget store. اختبر عدم إرسال payload الأصلي في logs/errors.
- **معيار الإغلاق:** إبقاء gateway مغلقًا حتى موافقة مستقلة؛ allowlist للغرض والحقول؛ تقليل البيانات قبل بناء prompt، وموافقة صريحة عند إرسال بيانات خارجية؛ مزود متعاقد/مراجع؛ اختبارات تسرب واحتفاظ/تسجيل لدى المزود.
- **الحالة:** FIXED_AND_TESTED فقط للإعداد الافتراضي المغلق حسب اختبارات الوحدة الموجودة؛ NOT_RUN لاختبار تسرب شامل/مزود حقيقي.

#### SEC-009 — أمن الويب وPWA لم يثبت على متصفح/جهاز

- **الدليل:** واجهة main هي prototype وتؤكد أنها لا تسجل الدخول ولا تحفظ أو ترسل بيانات؛ `app.js` لا يستخدم fetch/storage/geolocation/service worker. PR #32 غير مدمج ويجهز Manifest فقط، ويقر بأن HTTPS والجهاز الحقيقي لم يُختبرا. لا يوجد في main دليل على CSP أو سياسة نشر HTTPS أو فحص رؤوس أمان فعلي.
- **التصنيف:** VERIFIED — حدود prototype الحالية؛ UNKNOWN — رؤوس الاستضافة وTLS وCSP الفعلية.
- **الأثر:** لا يصح اعتبار prototype أو manifest دليلًا على أمان Web/PWA أو installability أو دعم background GPS.
- **الاختبارات المطلوبة:** `T-WEB-01`: تحقق من HTTPS/TLS وHSTS وCSP وframe-ancestors وX-Content-Type-Options وReferrer-Policy وPermissions-Policy في البيئة الفعلية. `T-WEB-02`: فحص DOM XSS/unsafe sinks وnavigation allowlist. `T-PWA-01`: اختبار install/launch على Android حقيقي بعد استضافة معتمدة، وتأكيد صلاحيات الموقع في foreground/background.
- **معيار الإغلاق:** اختيار/اعتماد استضافة؛ رؤوس أمان موثقة؛ CSP مناسبة دون `unsafe-eval` وتجنب `unsafe-inline` متى أمكن؛ اختبار متصفحات وأجهزة فعلية؛ سياسة Permissions-Policy؛ لا ادعاء بتثبيت أو تتبع خلفي قبل الاختبار.
- **الحالة:** NOT_RUN للبيئة الحقيقية.

### P2 — متوسط / تحسينات وضمانات تكميلية

#### SEC-010 — لا يظهر فحص آلي للأسرار/التبعيات في Workflows الحالية

- **الدليل:** Workflows backend/web في main تشغّل الاختبارات وtypecheck وJavaScript/Python static tests؛ لا يظهر في الملفين فحص secret scanning أو dependency audit مخصص. لا يعني ذلك عدم وجود إعدادات GitHub خارج الملفين.
- **التصنيف:** VERIFIED — غياب خطوة الفحص من هذين الـworkflowين؛ UNKNOWN — إعدادات المنصة الأخرى.
- **الأثر:** احتمال إدخال اعتماد ضعيف أو secret بالخطأ دون اكتشاف مبكر.
- **الاختبارات المطلوبة:** `T-SEC-CI-01`: PR تجريبي يحتوي canary secret غير صالح/وهمي في fixture آمن ويثبت أن الفحص يمنع الدمج/ينبه؛ لا تضع سرًا حقيقيًا. `T-DEP-01`: تقرير تبعيات وإصلاح CVEs وفق سياسة.
- **معيار الإغلاق:** تفعيل Secret Scanning/Push Protection إن كانت متاحة، فحص تبعيات دوري، تثبيت الإصدارات، مراجعة صلاحيات Actions بأقل امتياز؛ عدم كشف القيم في logs.
- **الحالة:** NOT_RUN.

#### SEC-011 — ضوابط Android/WebView لم تُحسم ولم تُختبر

- **الدليل:** لا يوجد تطبيق Android أصلي/حزمة WebView في main المفحوصة؛ وثائق A0 تقر أن التقنية لم تحسم في بعض المصادر. نموذج التهديد يقترح تعطيل file access وجسرًا أدنى وقائمة سماح.
- **التصنيف:** VERIFIED — لا حزمة Android ظاهرة في main؛ PROPOSED — ضوابط WebView على session/05.
- **الأثر:** أي تغليف مستقبلي غير مضبوط قد يتيح file access أو جسر JavaScript أو تنقلًا إلى نطاقات غير موثوقة.
- **الاختبارات المطلوبة:** `T-ANDROID-01`: تعطيل file/content access غير الضروري؛ منع mixed content؛ allowlist للـorigin/navigation؛ رفض الروابط الخارجية أو فتحها خارج WebView؛ اختبار الجسر والـdeep links؛ فحص أذونات الموقع.
- **معيار الإغلاق:** اعتماد التقنية؛ مراجعة إعدادات WebView أو native permissions؛ اختبار على جهاز حقيقي؛ عدم طلب إذن موقع قبل سياق وشرح وموافقة.
- **الحالة:** NOT_RUN.

## 5. خطة إصلاح مرتبة قابلة للاختبار

1. **قبل G0 / P0:** اعتماد MOSAAB لمتطلبات الهوية والجلسات، ثم تنفيذ مصادقة إنتاجية منفصلة عن shared development token. ربط هوية المالك بالجلسة فقط وإضافة اختبارات auth/IDOR شاملة.
2. **قبل بيانات حقيقية / P0:** اعتماد DB وhosting والقيود الأمنية؛ تطبيق persistence واختبارات العزل وإعادة التشغيل والتزامن وidempotency.
3. **قبل تشغيل فعلي / P0:** اعتماد سياسة Backup/Restore، تنفيذ استعادة فعلية معزولة، وقياس RPO/RTO. لا تكتفِ بالـRunbook.
4. **قبل GPS / P1:** حسم DEC-10/مدة الاحتفاظ/العينات والحذف؛ بناء consent state machine enforcement خادمي واختبارات السحب والإغلاق والخلفية.
5. **قبل رفع ملفات / P1:** اعتماد DEC-12/الأنواع والأحجام والاحتفاظ؛ تنفيذ تخزين خاص وفحص محتوى وownership واختبارات تنزيل.
6. **قبل التصدير / P1:** تحديد سياسة export/deletion/retention؛ تنفيذ ownership checks وaudit وإدارة الروابط.
7. **قبل تفعيل LLM / P1:** إبقاء default disabled؛ اعتماد البيانات والغرض والمزود والميزانية وموافقة المستخدم؛ إضافة اختبارات redaction/data minimization تشمل الأسماء والعناوين العربية.
8. **قبل استضافة Web/Android / P1:** تحديد رؤوس الأمن وTLS وCSP وPermissions-Policy وWebView allowlist، ثم فحوص متصفح/جهاز فعلية.
9. **تحسين مستمر / P2:** تفعيل secret/dependency scanning وتوثيق required checks بعد ظهورها فعليًا، مع مراجعة صلاحيات workflows.
