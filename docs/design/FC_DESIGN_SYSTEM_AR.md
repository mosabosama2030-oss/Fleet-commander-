# Fleet Commander — نظام التصميم وتجربة الذكاء الشخصي

> **الحالة:** PROPOSED — حزمة تصميم مرئي ومواصفات تسليم، وليست تنفيذًا تشغيليًا.  
> **المهمة:** FC-009 / Issue #10.  
> **الأساس:** `main` عند `8ba4511629cb6f64e21ce9a7537c034cf77a9660`.  
> **نطاق العمل:** تصميم الكابتن الفردي Web/PWA-first. لا يشمل إدارة أساطيل أو شاشات مديرين.

## 1. الفكرة التصميمية

**Fleet Commander هو مركز القيادة الشخصي للكابتن، وليس لوحة لإدارة أسطول.**  
التجربة تضع أهم قرار يومي في المقدمة: حالة الشيفت، ثم تسجيل الرحلات والمصروفات، ثم السجل والتقارير. ويظهر المساعد الذكي كطبقة تفهم السياق وتساعد الكابتن على اتخاذ القرار، لا كوكيل مستقل يتصرف بدلًا منه.

### اتجاه الهوية: Calm Command

- واجهة فاتحة هادئة، عملية، ذات كثافة معلومات منخفضة.
- كحلي عميق للثقة والوضوح، أخضر بحري للإجراء الأساسي، وبنفسجي محدود لتمييز الذكاء.
- لا مؤثرات زجاجية ثقيلة، ولا تدرجات كثيرة، ولا رسوم زخرفية تزاحم البيانات.
- لوحة RTL أصلية؛ القائمة الجانبية على اليمين في سطح المكتب، والتنقل السفلي على الهاتف.
- إظهار حالة المنتج الحقيقية في كل شاشة: متصل/غير متصل، مؤكّد/غير مؤكّد، فعّال/غير مفعّل.

## 3. نظام التصميم

راجع [ملف Design Tokens](./FC_DESIGN_TOKENS.json) وملفات المعاينة داخل [previews](./previews/).

### الألوان

| الاستخدام | Token | القيمة |
|---|---|---|
| خلفية التطبيق | canvas | `#F3F6F8` |
| سطح البطاقات | surface | `#FFFFFF` |
| النص الأساسي | ink | `#102A3A` |
| النص الثانوي | muted | `#6F8390` |
| الإجراء الأساسي | primary | `#087F7B` |
| تمييز المساعد الذكي | ai | `#635BCA` |

| تحذير/يحتاج قرارًا | warning | `#A66B16` |
| خطأ/رفض | danger | `#B33E46` |

لا يُستخدم اللون وحده للدلالة على الحالة؛ يرافقه نص ورمز واضحان.

### الخطوط

- الخط المقترح: IBM Plex Sans Arabic عند توفره محليًا، ثم Noto Sans Arabic، ثم Tahoma/system sans-serif.
- لا تحميل خطوط عبر CDN ولا اعتماد على اتصال خارجي لعرض النص.
- أرقام المبالغ والمعرّفات والتوقيت يمكن عزلها باتجاه LTR داخل الواجهة العربية.
- لا يقل النص الثانوي المهم عن 12px في المقاسات النهائية، مع تباين مقروء.

### القياسات والمكونات

- شبكة مسافات 4px؛ الحشوة الافتراضية للبطاقة 20px.
- نصف قطر البطاقة 16px، البطاقة البارزة 20–24px، والحقول 12px.
- ارتفاع الزر 48px والحقول 52px، والهدف اللمسي لا يقل عن 44×44px.
- حالات المكوّنات: default, hover, focus-visible, disabled, loading, success, warning, error.
- استخدم CSS logical properties مثل `margin-inline` و`inset-inline` لتجنب كسر RTL.
- احترام `prefers-reduced-motion`، وعدم استخدام الحركة لإيصال معلومة أساسية.

## 5. تصميم الشاشة الرئيسية

**الهدف:** إجابة سريعة عن ثلاث نقاط: ما حالة يومي؟ ما الخطوة التالية؟ وهل يوجد شيء يحتاج انتباهي؟

ترتيب المحتوى:
- تحية موجزة وعنوان «مساحة قيادة يومك».
- بطاقة حالة الشيفت بأوضح موضع، مع إجراء واحد أساسي يتغير حسب الحالة المؤكدة من الخادم.
- ملخص تشغيلي للرحلات والمصروفات والنشاط؛ لا تعرض قيمًا أو مجاميع قبل جلب بيانات موثوقة.
- بطاقة المساعد الشخصي: وضع التشغيل ظاهر دائمًا، وزر الدخول للمساعد لا يوحي بأنه متصل إذا كان Gateway مغلقًا.
- آخر النشاط مع مصدر وتوقيت كل حدث.
- إجراءات سريعة لإضافة رحلة أو مصروف عند توقف المركبة.

في غياب API: استخدم Empty/Not connected state. لا تملأ البطاقات بأرقام تجريبية ولا تعرض «0» بدل «غير متاح».

## 6. الشاشات المطلوبة

### 6.1 تسجيل الدخول

- شعار واسم Fleet Commander، وصف قصير يركز على الخصوصية والتحكم الشخصي.
- بريد إلكتروني، كلمة مرور، إظهار/إخفاء محلي، «تسجيل الدخول»، «نسيت كلمة المرور؟».
- رسائل منفصلة للتحقق المحلي، رفض المصادقة، انتهاء الجلسة، وانقطاع الشبكة.
- لا تؤكد الدخول ولا تعرض الرئيسية قبل تأكيد الخادم؛ لا تحفظ كلمة المرور في التخزين المحلي.

### 6.2 الشيفت — قبل البدء

- بطاقة مركبة نشطة واحدة فقط عند تأكيدها من الخادم.
- فحص جاهزية مختصر: حالة المركبة، اتصال الخدمة، وبيانات البداية التي يعتمدها المنتج.
- زر «بدء الشيفت» لا يتحول إلى نجاح قبل إقرار الخادم.
- أي حقل مثل قراءة العداد أو صورة البداية يظل قابلًا للضبط بعد اعتماد متطلباته، ولا يُفرض من التصميم وحده.

### 6.3 الشيفت — أثناء العمل / الإنهاء

- حالة OPEN ظاهرة مع تاريخ بداية الشيفت.
- أزرار كبيرة: «إضافة رحلة»، «إضافة مصروف»، «إنهاء الشيفت».
- تفاعل أقل أثناء القيادة؛ تظهر ملاحظة ثابتة لإدخال البيانات عند التوقف في مكان آمن.
- شاشة مراجعة قبل الإنهاء؛ لا تحسب صافيًا ولا تعرض دخلًا نهائيًا حتى اعتماد DEC-03/05/09.
- حالة OUTCOME_UNKNOWN عند timeout: لا نجاح ولا فشل افتراضي ولا إعادة إرسال صامتة.

### 6.4 تسجيل رحلة

- نموذج قصير يدوي: المنصة/المصدر، المبلغ كما أدخله الكابتن، وقت الرحلة، وملاحظة اختيارية إذا اعتمدت.
- الإلزامية، العملة، التقريب، والحقول النهائية تظل UNKNOWN لحين اعتماد العقد والقرارات.
- الحالة بعد الإرسال: «جارٍ الإرسال» ثم «تم التأكيد» فقط عند رد الخادم.
- لا استيراد من تطبيقات النقل ولا تنبؤ بقيمة الرحلة.

### 6.5 المصروفات

- إدخال يدوي واضح، وتصنيف فقط من قائمة معتمدة.
- إرفاق صورة فاتورة قدرة مستقبلية؛ لا يظهر زر فعّال قبل تنفيذ رفع الملفات وقرار الاحتفاظ.
- لا تقترح الواجهة خصمًا أو صافيًا أو معادلة مالية.

### 6.6 السجل

- قائمة زمنية للشيفتات والرحلات والمصروفات.
- شارة حالة لكل سجل: مؤكد، ملغى مع سبب، أو يحتاج مراجعة.
- التصحيح يظهر كحدث جديد مرتبط بالأصل؛ لا تعدّل التاريخ بصمت.

### 6.7 التقارير

- مرشحات فترة واضحة، ثم ملخصات تشغيلية يمكن إثبات مصدرها.
- أي مجاميع مالية أو صافي أو مستحقات تبقى مخفية/موقوفة حتى اعتماد قواعد الحساب والعملة والتقريب.
- كل مقياس يعرض تعريفه، نطاقه الزمني، ومصدره.

### 6.8 موافقة GPS

- شرح «لماذا نطلب الموقع؟» قبل طلب إذن المتصفح.
- اختيار موافقة صريح، مع حالة «لم يُطلب / مرفوض / فعّال أماميًا / متوقف».
- لا يبدأ التتبع افتراضيًا ولا يظهر كخدمة خلفية مضمونة في PWA.
- مدة الاحتفاظ، فواصل العينات، وسلوك سحب الموافقة UNKNOWN جزئيًا؛ يجب عرضها بعد اعتماد DEC-10 فقط.

### 6.9 مركز الذكاء الشخصي

**التصور المقترح:** مساعد عربي يفهم سياق الكابتن من البيانات التي يسمح بها المنتج، ويقدم شرحًا واقتراحًا قابلًا للتحقق.

طبقات القدرة:
1. **سياق موثوق:** حالة الشيفت والسجلات المؤكدة فقط؛ لا تخمين لحالة غير معروفة.
2. **فهم اللغة:** إدخال نصي، ثم صوتي عند اكتمال الميكروفون وTTS وأذونات المتصفح.
3. **فهم المستندات:** قراءة صورة فاتورة/إيصال كقدرة مستقبلية، مع عرض النص المستخرج قبل الاعتماد.
4. **الاستدلال:** يوضح الدليل الذي بنى عليه كل اقتراح؛ يميّز الحقيقة عن الاستنتاج.
5. **الاقتراح:** يشرح الخيارات ولا ينشئ إجراءً أو مبلغًا من تلقاء نفسه.
6. **التنفيذ:** لا يحدث إلا عبر API مخوّلة وبعد تأكيد الكابتن، ثم تأكيد الخادم.
7. **الذاكرة:** لا تُحفظ تفضيلات أو سياقات حساسة إلا بسياسة موافقة واحتفاظ معتمدة.

**دورة القرار:** بيانات مسموح بها ← سياق ودليل ← اقتراح واضح ← مراجعة وتأكيد الكابتن ← تنفيذ عبر Backend ← نتيجة مؤكدة وسجل تدقيق.

### حدود الذكاء الحالية

- VERIFIED: توجد نواة Voice rule-first ومسار LLM مساعد، مع تحقق صارم من النية والأرقام ورفض أي intent غير مسموح.
- VERIFIED: `LlmGateway` نقطة مرور واحدة، ويبدأ مغلقًا افتراضيًا؛ فشل Gateway يرجع لمسار القواعد.
- UNKNOWN/NOT RUN: الميكروفون الفعلي وTTS، جودة اللهجة على أجهزة حقيقية، قراءة الصور، ذاكرة دائمة، وتكامل المساعد داخل الواجهة.
- PROPOSED: شاشة المساعد المرئية في هذا التصميم.
- لا تعرض هذه المعاينة أن «الذكاء الخارق» مفعل الآن؛ حالة المساعد في التصميم «غير مفعّل — بانتظار قرارات الأمان والخصوصية والربط». لا Provider حي ولا اتصال مدفوع ضمن هذا التسليم.

## 7. حالات التصميم المشتركة

| الحالة | النص/العرض | الممنوع |
|---|---|---|
| Loading | «جارٍ تحميل بياناتك…» مع مؤشر غير مزعج | عرض محتوى قديم على أنه مؤكد |
| Empty | سبب الفراغ وخطوة تالية واضحة | أرقام صفرية مضللة |
| Submitting | «جارٍ الإرسال…» وتعطيل التكرار | إظهار نجاح مسبق |
| Confirmed | تأكيد الخادم مع وقت/مرجع | استنتاج نتيجة مالية إضافية |
| Error | رسالة عربية محددة وخطوة تصرف | رسالة Stack trace أو كشف داخلي |
| Outcome unknown | «لم نتمكن من تأكيد نتيجة العملية» | افتراض النجاح أو إعادة الإرسال تلقائيًا |
| Not connected | «هذه الشاشة غير متصلة بالخادم بعد» | مؤشر أخضر يوحي باتصال فعلي |
| AI disabled | «المساعد الذكي غير مفعّل حاليًا» | تمثيل إجابة مولدة أو وسم «AI نشط» |

## 8. السلامة وإمكانية الوصول

- لا تضع إدخالًا طويلًا أو رسومًا تفاعلية أو محادثة مطولة ضمن وضع القيادة.
- كل حالة لها نص ورمز، لا لون فقط.
- ترتيب Tab يطابق ترتيب القراءة RTL، وكل زر له اسم قابل لقارئ الشاشة.
- دعم تكبير 200% وعدم قص النصوص العربية.
- الحقول تحمل label مرئيًا؛ رسالة الخطأ مرتبطة بالحقل.
- عند فقد الشبكة لا يوجد Offline queue أو إرسال تلقائي لاحق.
- لا يتم طلب GPS أو الميكروفون أو الكاميرا بمجرد فتح الشاشة.
